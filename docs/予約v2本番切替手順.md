# 予約 UI・予約ロジック 本番切替手順

## 現在の状態

このリポジトリには、スマホ向け UI 改善と予約 v2 が入っていますが、本番には未適用です。

予約 v2 は、GAS のコードを配置しただけでは有効になりません。Script Properties に切替値がない場合は必ず `LEGACY`（旧方式）で動きます。新方式は Apps Script エディタから `enableReservationV2Release()` を明示的に実行した場合だけ有効になります。

## 変更内容

- 3秒で先に「予約完了」を表示する処理を廃止
- スプレッドシート行とカレンダー予定が確定した `active` 応答だけを完了表示
- `request_id` を使った二重送信防止
- 通信切断・タイムアウト時の状態確認と、同じ `request_id` による安全な再試行
- 予約競合の確認を Script Properties の軽量索引へ移動
- Script Lock 内では枠確保と処理中行の保存だけを行い、遅いカレンダー処理はロック外で実行
- 管理者の取消確定時に索引を自動解放
- 会議室構成を変更した場合は索引を安全停止し、再構築が終わるまで予約を受け付けない
- スマホのヘッダー、カード間隔、入力サイズ、セーフエリア、管理表の横スクロールを調整

## 本番適用前チェック

1. 本番スプレッドシートをバックアップします。
2. 現在の GAS デプロイ版と静的サイトのコミットを記録します。
3. ローカルで次を実行し、すべて成功することを確認します。

   ```bash
   node tests/reservation_v2_unit_test.mjs
   node tests/reservation_v2_mock_integration_test.mjs
   node tests/release_readiness_test.mjs
   git diff --check
   ```

4. `getReservationV2ReleaseStatus()` の実行結果を保存します。

## 安全な適用順序

### 1. GAS コードを配置する

次のファイルを Apps Script プロジェクトへ反映します。

- `gas/Setup.gs`
- `gas/Api.gs`
- `gas/ReservationV2.gs`
- `gas/TestEnvironment.gs`
- `gas/appsscript.json`

新しい Web アプリ版を作成します。この時点ではプロパティ未設定なので予約は旧方式のままです。

### 2. シート列だけ準備する

Apps Script エディタから次を実行します。

```text
prepareReservationV2Release()
```

`予約` シートの末尾に次の列が追加されます。既存行の予約内容は変更されません。

- リクエストID
- リクエストハッシュ
- 処理開始日時
- 更新日時
- エラー内容

戻り値が `mode: "LEGACY"`、`enabled: false` であることを確認します。

### 3. UI を公開する

HTML 5ファイル、`dark.css`、`responsive.css`、`config.js`、`dark.js` を同じリリースとして公開します。

GAS が `LEGACY` の間、予約画面は旧 API と互換動作します。ただし、旧来の「3秒後に未確定でも完了表示する処理」は使わず、実際の API 応答を待ちます。

### 4. 予約 v2 を有効化する

利用の少ない時間に Apps Script エディタから次を一度だけ実行します。

```text
enableReservationV2Release()
```

この関数は次を一つの Script Lock 内で行います。

1. 新規予約受付を短時間 `PREPARING` にする
2. 最新の予約シートから競合索引を再構築する
3. 索引準備完了を記録する
4. `V2` に切り替える

戻り値が次の状態であることを確認します。

```text
mode: "V2"
enabled: true
index_ready: true
```

### 5. スモークテスト

本番で許容できるテスト枠を使い、以下を確認します。

1. 予約1件が完了画面、予約シート、対象カレンダーのすべてに1件ずつ作成される
2. 同じ時間・同じ会議室の2回目が競合エラーになる
3. 別会議室または別時間の予約が待たされず登録される
4. 予約確定直後にページを再読み込みしても同じ予約が2件作られない
5. 管理者取消後、同じ枠が再予約できる

## ロールバック

予約 v2 だけを旧方式へ戻す場合、Apps Script エディタから次を実行します。

```text
disableReservationV2Release()
```

処理中の予約が残っている場合、この関数は切替を拒否します。数秒待って再実行し、`mode: "LEGACY"`、`enabled: false` を確認してください。既に開いている予約画面が v2 のまま送信した場合は、予約を作らず再読み込みを案内するため、旧方式への切替直後にも二重予約は発生しません。

UI も戻す場合は、その後に静的サイトを直前のコミットへ戻します。追加済みの予約シート列は旧方式では使われないため、削除する必要はありません。

## 運用上の注意

- `予約` シートを手作業で追加・変更した後は `rebuildReservationV2Indexes()` を実行します。
- v2 有効中に会議室構成を変更すると安全のため索引が無効になります。変更後に `rebuildReservationV2Indexes()` を実行し、`index_ready: true` を確認します。
- `キャンセル依頼` は管理者が取消を確定するまで枠を保持します。管理者取消時の索引解放は自動です。
- `PREPARING` または索引未準備中は予約を作らず、利用者へ再試行を案内します。
- 状態確認には `getReservationV2ReleaseStatus()` を使います。

## 検証済み性能の目安

隔離テスト環境の100論理リクエストでは、二重予約と欠落は0件でした。GAS 内の処理時間は中央値約3.7秒、95パーセンタイル約8.5秒、最大約10.4秒でした。高負荷時はクライアント側の再試行待ちが長くなるため、UI は90秒まで状態を確認し、それでも確定できない場合は完了表示せず「結果不明」として同じ `request_id` を保持します。
